# 4시 40분의 용사 개선 PRD

자동 전투와 교사 테마를 바탕으로, 성장 선택을 이해하기 쉽고 자리를 비운 뒤에도 진행을 파악할 수 있는 게임으로 개선한다. 앞서 제안한 10개 개선안을 기존 JavaScript 구조, 저장 호환성, 전투 규칙에 연결한다. GitHub Pages에서 실행되는 정적 웹앱을 유지한다.

## 0 개발할 때 먼저 읽을 안내

이 PRD는 10개 기능의 상세 요구사항과 개발 기준을 함께 관리한다. 각 작업에서는 아래 위치에서 필요한 절을 선택해 읽는다. 해당 기능의 완료 기준과 영향을 받는 공통 규칙까지 확인한다.

| 확인할 내용 | 읽을 위치 |
| --- | --- |
| 제품 목표·범위·제공 순서 | 1·3절 |
| 현재 코드와 공통 실행 구조 | 2·6절의 관련 부분 |
| 이번에 구현할 기능 | 5절의 해당 FR01~FR10 |
| 저장 필드·보존·거래 | 7절과 해당 FR의 저장 규칙 |
| 화면·입력·오프라인·배포 | 4·8절의 관련 부분 |
| 수용 검사·단계 완료 | 9·10절 |
| 읽기 범위·짧은 작업 기록·토큰 절약 | 11절 TE01~TE07 |
| 현재 동작과 개발 지침의 근거 | 12절 |

개발 AI 토큰은 입력·출력에 사용되는 토큰을 뜻한다. 게임의 연수학점인 `token`은 기존 의미를 유지한다. 개발을 시작할 때는 적용되는 저장소 지침과 실제 변경 상태를 확인하고, 10절에서 구현·검증이 남은 첫 단계부터 진행한다. 진행 중인 작업이 있으면 인계 기록을 실제 코드와 비교한다. 기능별 코드 탐색의 시작점은 TE03, 바로 사용할 개발 지시문은 11절 끝에 있다.

### 현재 기능과 규칙

- 소개 화면에서 남교사와 여교사를 선택한다. 두 캐릭터의 기본 전투 능력은 같다.

- 자동 공격은 기본적으로 초당 한 번 실행된다. 추가 공격은 마우스·터치·Enter·Space와 길게 누르기를 지원한다.

- 기본 경험치는 초당 5다. 레벨마다 전체 공격력 배율이 5%씩 증가한다.

- 아이템은 24종이며 각 Lv.25까지 강화한다. 유물은 20종이고 미보유 항목 중에서 뽑는다. 업적은 30개다.

- 동료는 체육 요정인 `comp.na`와 응원 요정인 `comp.yu`다. 현재 두 동료의 효과가 함께 계산된다.

- 10마리 처치마다 게임 속 시간이 1분 진행된다. 보스는 100마리 처치마다 등장한다. 기본 보스 제한 시간은 실제 시간 30초다.

- 반짝 분필은 빠른 추가 공격을 발생시킨다. 칭찬의 마법은 추가 공격의 치명타 확률을 일시적으로 100%로 만든다. 자동 공격 자체는 치명타 판정을 하지 않는다.

- 자리비움은 최대 24시간 정산한다. 경험치는 100%, 전투 골드는 70%를 지급한다. 자리비움에 수동 공격과 반짝 분필 공격은 포함하지 않는다.

- 다음 모험은 현재 `min`만큼 연수학점을 더한다. 연수학점 배율은 `1 + token × 0.1`이다.

- 저장 키는 `ys_bugfree_final_v2`, 현재 저장 버전은 4다. 정상적인 이전 저장 변환, 손상 데이터 원본 보존, 백업, 다중 탭의 저장 소유권 처리가 있다. [S1] [S2] [S3] [S6]

### 개선 전에 해결해야 할 연결 지점

**저장 필드를 추가하는 방식부터 정해야 한다.** `Data.normalize()`는 v3와 v4의 필수 항목을 `Object.keys(createDefault())`로 검사한다. 새 기본 필드를 추가하면서 이 검사를 유지하면 정상적인 이전 저장도 필드 누락으로 거절될 수 있다. 버전별 필수 항목과 마이그레이션을 분리한다. [S2]

**복귀 보고서는 정산하는 순간 생성해야 한다.** `GameApp.prepareIntroProgress()`는 소개 화면에서 `Logic.advance(..., {offline:true, silent:true})`로 이미 보상을 반영한다. 이때 반환되는 결과를 기록해야 한다. `enterGame()`에서 처음 전후 차이를 구하면 성과를 놓칠 수 있다. [S4]

**보스 준비는 전투 상태로 구현해야 한다.** `Sys.showDialog()`는 반복 입력만 중단한다. 게임 루프와 보스 제한 시간은 계속 흐른다. 준비 대화상자만 추가해서는 제한 시간 시작을 제어할 수 없다. [S4]

**자동 구매를 기존 오프라인 반복문에 바로 추가하면 안 된다.** 현재 `Simulation.simulate()`는 자리비움 골드를 마지막에 `initialGold + floor(goldGross × 0.7)`로 반영한다. 정산 도중 구매를 끼우면 차감액이 덮어써질 수 있다. 이번 버전의 자동 구매와 자동 스킬은 화면이 보이는 플레이에 적용한다. [S3]

**반복 갱신 중에는 조작 중인 DOM을 유지해야 한다.** `CatalogUI`는 구매 버튼을 한 번 만들고 갱신한다. 업적 화면은 달성·수령 상태로 만든 signature를 사용하므로 숫자 진행도를 추가할 때 갱신 조건도 바꿔야 한다. [S4] [S5]

**첫 방문 뒤 오프라인 실행을 검증해야 한다.** 현재 `APP_SHELL`에는 핵심 게임 JS, CSS, 전투 SVG가 빠져 있다. 신규 자산과 함께 필수 파일을 선캐시에 포함한다. 실제 오프라인 동작은 빈 캐시부터 확인한다. [S7]

## 4 사용자 흐름과 화면 배치

새 이용자는 소개 화면에서 캐릭터를 선택한 뒤 모험을 시작한다. 짧은 안내를 따라 자동 전투를 확인하고 첫 강화를 선택한다. 이후 고정한 업적과 다음 보스 안내를 보며 진행한다. 안내는 건너뛰거나 다시 볼 수 있다.

기존 이용자는 소개 화면에서 저장된 모험을 확인한다. 자리비움 정산은 저장 소유권을 확인한 뒤 한 번 수행한다. 모험에 들어오면 해당 보고서를 보여 준다. 보고서를 닫은 뒤에도 설정에서 다시 볼 수 있다.

모험 중에는 성장·동료·아이템·유물·업적·설정의 기존 6개 탭을 사용한다. 새 기능은 다음 위치에 배치한다.

| 위치 | 추가할 요소 |
| --- | --- |
| 전투 상단 | 현재 장소, 학교 지도 버튼, 다음 보스 안내 |
| 전투 하단 | 고정 목표 최대 3개, 현재 자동화 상태 |
| 성장과 아이템 탭 | 구매 전후 비교, 수량 선택, 추천 이유 |
| 동료 탭 | 동료 목록, 동행 2슬롯, 조합 저장과 불러오기 |
| 업적 탭 | 진행도, 고정 선택, 받을 수 있는 보상, 모두 받기 |
| 설정 탭 | 자동화, 꾸미기, 최근 보고서, 첫 모험 안내 다시 보기, 다음 모험 |
| 별도 대화상자 | 지도, 보스 준비, 복귀 보고서, 정산 미리보기, 꾸미기 |

320px 화면에서도 지도·고정 목표·보스 준비·보고서로 진입할 수 있어야 한다. 모바일에서 숨겨지는 기존 `.goal-card`에 핵심 기능의 유일한 진입점을 두지 않는다. [S8]

## 5 기능별 요구사항

### FR01 첫 모험 안내

**사용자 목적:** 처음 접속한 사람이 전투 방식과 첫 성장 목표를 이해한다.

1. 첫 게임 시작 후 자동 전투 관찰, 첫 강화, 반짝 분필 사용, 업적 확인의 네 단계를 제공한다. 실제 버튼을 조작할 수 있는 비모달 안내로 표시한다.

2. 안내는 조건을 충족한 단계를 자동 완료한다. 이미 수행한 행동을 다시 강제하지 않는다.

3. 건너뛰기와 닫기를 제공한다. 설정에서 다시 볼 수 있다.

4. 안내 문구는 “몬스터 10마리를 처치하면 게임 속 시간이 1분 진행됩니다”로 표현한다. 보스와 스킬에는 실제 초 단위를 표시한다.

5. 기존 `hasStarted=true` 저장에서는 강제 안내를 시작하지 않는다. 새 필드를 보완하고 다시 보기 기능을 제공한다.

6. 안내 상태는 저장하되 안내 완료에 별도 재화 보상을 연결하지 않는다.

**구현 연결:** `GameApp.enterGame()`, `renderIntro()`, `RepeatInput`, 신규 `ExperienceUI` 안내 컴포넌트. 자동 전투 관찰은 실제 자동 공격 사건, 첫 강화와 스킬은 성공한 실행 사건, 업적 확인은 해당 탭을 연 행동으로 완료한다. 안내 창을 표시했다는 이유만으로 모든 단계를 완료 처리하지 않는다.

**완료 기준:** 신규 저장에서 안내를 완료하거나 건너뛸 수 있다. 새로고침 후 완료 상태가 유지된다. 이전 저장은 안내 때문에 차단되지 않는다. 소개 화면 대기에는 경험치와 전투가 발생하지 않는다. 안내를 닫으면 원래 버튼에 포커스가 돌아간다.

### FR02 강화 효과 미리보기와 추천 및 묶음 구매

**사용자 목적:** 같은 골드로 어떤 성장을 얻는지 확인하고 구매한다.

1. 기본 강화와 아이템에 현재 값, 구매 후 값, 변화량, 실제 구매 수량, 총비용을 표시한다.

2. 수량은 1회, 10회, 최대를 제공한다. 골드 부족이나 최대 레벨 때문에 10회를 모두 구매할 수 없으면 실제 가능한 수량을 표시한다.

3. 미리보기와 실제 구매는 같은 순수 계산 함수를 사용한다. 기존 비용 증가와 단계별 반올림, 강화 적용 순서를 그대로 계산한다.

4. 실행 시에는 경과 전투를 한 번 반영한 뒤 최신 상태로 견적을 다시 계산한다. 전체 구매 결과를 하나의 후보 상태로 만들고 한 번 저장한다.

5. 방치 중심 추천에는 자동 공격 계열을 우선 비교한다. 직접 조작 중심 추천에는 추가 공격과 치명타의 기대 효과를 비교한다. 경험치·골드·보스 시간은 별도 목표로 비교한다.

6. 추천 옆에 이유를 표시한다. 예를 들어 “현재 골드로 자동 공격 증가량이 가장 큽니다”처럼 비교 기준을 알린다. 실측하지 않은 ‘최적 전략’이라는 표현은 사용하지 않는다.

7. 일반 치명타 총합 50% 상한과 칭찬의 마법에 의한 일시적 100%를 구분한다. 자동 공격에 치명타 증가 효과가 있다고 표시하지 않는다.

8. 최대 구매의 반복 횟수는 해당 레벨 상한 이하로 제한한다. 수치 계산은 기존 `GameLimits`를 사용한다. 길게 누르기 반복 구매는 1회 모드에서만 유지한다. 수량 선택과 10회·최대 구매는 한 번의 입력으로 한 번 실행한다.

**구현 연결:** `Logic.getUpgrade()`, `upgrade()`, `buyItem()`, `Catalog.itemCost()`, `Catalog.bonuses()`, `Simulation.getAutoDamage()`와 `getClickDamage()`를 재사용한다. `Progression.quotePurchase()`와 `applyPurchase()`를 제안한다. 기존 구매 API는 이 공통 경로를 호출한다.

**완료 기준:** 같은 상태에서 미리보기의 수량·총비용·구매 후 수치가 실제 결과와 일치한다. 미리보기 계산 자체는 구매·보상·경험치 지급을 실행하지 않는다. 대화상자 뒤에서 계속되는 정상 전투의 변화는 별도로 반영한다. 잔액은 음수가 되지 않는다. 치명타 상한에서 효과를 과장하지 않는다. 길게 누르기 중 버튼 DOM이 교체되지 않는다.

### FR03 자동 강화와 스킬 사용 조건

**사용자 목적:** 성장 방향과 사용 예산을 정해 두고 가끔 진행을 확인한다.

1. 자동 강화는 기본 꺼짐으로 제공한다. 전략은 골드 모으기, 자동 공격 우선, 선택 항목 균형 성장이다. 골드 모으기는 자동 구매를 하지 않는다. 자동 공격 우선은 구매 가능한 대상 중 골드당 자동 공격 증가량이 가장 큰 항목을 선택하고 같은 점수이면 고정 ID 순서를 사용한다. 균형 성장은 선택한 항목을 순환하며 한 단계씩 구매하고, 현재 살 수 없는 항목은 건너뛴다. 마지막 순환 위치를 저장한다.

2. 사용자는 자동 구매 대상, 전체 사용 한도 `budgetLimit`, 남겨 둘 골드 `reserveGold`를 설정한다. 이미 사용한 금액 `budgetSpent`와 남은 한도는 시스템이 계산해 읽기 전용으로 표시한다.

3. 자동 구매는 `cost <= budgetLimit - budgetSpent`이면서 구매 후 골드가 `reserveGold` 이상일 때만 실행한다.

4. 사용액은 재접속이나 다음 모험으로 자동 초기화하지 않는다. 한도를 수정해도 사용액을 유지한다. 별도의 ‘예산 새로 시작’ 동작에서 새 한도를 확인한 경우에만 사용액을 0으로 만든다.

5. 자동 스킬은 스킬별로 직접 사용, 준비되면 사용, 보스에게 사용을 제공한다. 칭찬의 마법 자동 사용은 반짝 분필이 활성 상태이거나 같은 결정에서 함께 시작할 때로 제한해 공격 없이 버프만 소모하지 않게 한다.

6. 화면이 보이고, 모험이 시작되어 있으며, 저장 소유권과 정상 저장 기능이 있을 때 작동한다. 소개 화면, 숨겨진 탭, 복구 상태, 다른 탭 소유, 거래 대화상자, 저장 실패 상태에서는 새 자동 구매와 자동 스킬을 중지한다.

7. 이번 버전은 자리비움 정산 중 자동 구매와 신규 스킬 발동을 수행하지 않는다. 화면에는 “자동 강화와 스킬은 이 화면이 열려 있을 때 작동합니다”라고 안내한다.

8. 자동 결정은 렌더링 함수와 분리한다. 현재 시점에서 최대 초당 한 번 결정하며 한 결정에서는 최대 10회의 강화만 구매한다. 긴 프레임 지연이나 복귀 뒤 놓친 결정 횟수를 몰아서 실행하지 않는다. 전투 정산은 기존 규칙대로 수행하며, 자동 구매량은 화면 지연에 따라 줄어들 수 있다.

9. 보석 소비, 유물 뽑기, 업적 수령, 다음 모험 시작, 초기화는 자동화 대상에서 제외한다.

10. 자동 구매는 골드 차감, 강화 결과, 예산 사용액을 같은 저장 단위로 반영한다. 자동 스킬도 영구 저장 성공 후 확정한다. 저장에 실패하면 해당 자동 행동 후보를 적용하지 않고 중지 사유를 표시한다. 기존 수동 임시 플레이 정책은 유지한다.

**구현 연결:** 신규 `AutomationEngine.tick()`을 전투 정산 이후 실행한다. 구매는 FR02의 공통 계산을 사용한다. `UI.renderRes()`와 `UI.renderSkills()`는 상태를 표시하기만 한다. 기존 `Logic.commit()`의 임시 저장 허용 동작을 검토하고, 자동 구매에는 영구 저장 성공이 필요한 경로를 사용한다.

**완료 기준:** 예산 1,000, 사용액 900인 상태에서 비용 150의 자동 구매는 발생하지 않는다. 숨겨진 탭에서 자동 구매·자동 스킬·예산 사용액이 증가하지 않는다. 수동 구매 이후에도 최신 잔액을 사용한다. 새로고침과 정산으로 한도가 복원되지 않는다. 렌더링을 추가로 호출해도 구매가 늘지 않는다. 긴 프레임 뒤에도 밀린 자동 결정을 재생하지 않는다.

### FR04 보스 준비와 실패 원인 안내

**사용자 목적:** 보스 도전 시점과 성장 방향을 선택한다.

1. 진입 방식은 자동 도전과 준비 후 도전을 제공한다. 기본값과 이전 저장의 기본값은 자동 도전이다.

2. 보스 등장 직전에는 남은 처치 수, 사용 가능한 스킬, 현재 자동 공격 기준의 예상 결과를 표시한다.

3. 준비 후 도전에서는 보스를 생성하되 `pending` 상태로 둔다. 도전 버튼을 눌렀을 때 제한 시간을 시작한다. 준비 창을 닫아도 대기 상태를 유지하며, 전투 카드에 ‘보스 도전 시작’ 버튼을 계속 표시한다. ‘강화하러 가기’는 준비 창을 닫고 성장 탭으로 이동한다.

4. 준비 중에는 경험치와 스킬 재사용 시간은 흐른다. 공격, 처치, 골드 지급, 보스 보상, 수동 공격 누적 업적은 증가하지 않는다. 보유 골드로 강화하거나 동료 조합을 바꾸는 것은 허용한다. 새로운 스킬 시전은 막는다.

5. 대기 중 자동 공격과 스킬 공격의 밀린 횟수를 축적하지 않는다. 도전 시작 시 한꺼번에 공격하지 않는다.

6. 활성 보스는 페이지 새로고침이나 대화상자 열기로 제한 시간이 초기화되지 않는다. 전투 중 진입 방식 변경은 다음 보스부터 적용한다.

7. 실패할 때 보스 최대 체력, 남은 체력, 실제 제한 시간, 도전 시 자동 공격, 스킬 사용 여부를 기록한다. 공격력·시간·스킬 활용에 연결된 다음 행동을 안내한다.

8. 현재 보스 실패 후 `min`과 `kills`가 1씩 감소하는 규칙을 기본으로 유지한다. 되돌아간 진행과 실패 기록을 함께 표시한다.

9. 예측은 복제본을 가상의 `active` 상태로 만들고 가상의 시작 시각·제한 시각을 설정한 뒤 기존 전투 계산을 사용한다. “현재 조합의 자동 공격과 시간에 따른 레벨 성장 기준 예상”으로 표시한다. 자동 구매, 수동 추가 공격, 반짝 분필 공격, 신규 스킬 시전은 포함하지 않으며 해당 보스의 성공·실패가 결정되면 계산을 끝낸다. 실제 상태·도전 ID·저장·보상은 변경하지 않는다.

**상태 규칙:** `pending`에서는 `mob.boss=true`, `mob.deadline=0`을 허용한다. `Simulation.reconcile()`은 대기 상태에 제한 시간을 자동 생성하지 않고, `expireBoss()`는 `active`만 만료시킨다. `simulate()`의 제한 시간 사건도 `active`일 때만 선택한다. 대기 중 값 0을 다음 사건으로 선택하면 반복문이 진행하지 않을 수 있으므로 그 외 상태의 제한 시간 사건은 `Infinity`로 취급한다. 일반 전투 도중 `pending`으로 바뀌면 즉시 자동·반짝 분필 공격 사건을 제외하고 경험치 사건만 남긴다. 피해 함수뿐 아니라 공격 사건 집계와 `Combat.attack()`의 누적 클릭도 공통 허용 조건으로 차단한다. 도전 시작 시 공격 시계를 현재 시점에서 재개한다. 기존 진행 중 보스는 체력과 제한 시각을 보존해 `active`로 변환한다.

**도전 시작:** `startBoss()`는 최신 상태가 `pending`일 때만 실행한다. 저장 성공 시 하나의 도전 ID, 시작 시각, 제한 시각을 확정한다. 이미 `active`인 상태에서 다시 호출하면 이 값을 변경하지 않는다. 저장 실패 시 대기를 유지한다.

**완료 기준:** 준비 상태의 60초·24시간 시뮬레이션과 같은 호출 안의 일반 적→대기 전환이 모두 정상 종료한다. 준비 화면에서 기다리는 동안 보스 제한 시간과 체력이 소모되지 않고 골드·처치·누적 클릭 보상이 늘지 않는다. 도전 후에는 실제 시간이 흐른다. 새로고침해도 남은 제한 시간이 보존된다. 실패 안내의 체력은 실패 순간 값이다. 제한 시각과 같은 시각의 공격 처리 순서는 기존 규칙을 유지한다.

### FR05 학교 모험 지도

**사용자 목적:** 성장에 따라 새로운 장소와 이야기를 만난다.

1. 첫 버전은 교실, 도서관, 과학실, 체육관, 학교 정문의 5개 장소를 제공한다.

2. 현재 전투 장소와 영구 해금한 장소를 구분한다. 전투 장소는 이번 모험의 보스 격파 기록으로 결정한다. 지도에서 다른 장소를 누르면 설명과 배경을 미리 볼 수 있다.

3. 100, 200, 300, 400 처치 구간의 보스를 격파했는지 이번 모험의 checkpoint로 기록한다. `min`이나 누적 `bossKills`만으로 해금하지 않는다.

4. 교실에서 시작하고 첫 보스 격파 후 도서관, 두 번째 후 과학실, 세 번째 후 체육관, 네 번째 후 학교 정문에 도착한다.

5. 게임 속 16:40 도달과 네 번째 보스 격파를 별도 사건으로 표시한다. 현재 계산상 400번째 처치에서 목표 시각에 도달하고 다음 적이 보스가 되므로, 목표 시각 도달만으로 최종 보스를 처치했다고 표시하지 않는다.

6. 장소마다 배경 1개, 짧은 설명, 입장 문장, 보스 격파 문장을 제공한다. 이야기 창은 방치 진행을 막지 않는다. 지나간 이야기는 지도에서 다시 본다.

7. 영구 해금과 본 이야기 기록은 정산 후 유지한다. 이번 모험의 이동 기록은 초기화한다. 네 번째 보스 이후에는 자유 모험을 계속할 수 있다.

8. 기존 저장은 현재 `kills`가 101, 201, 301, 401 이상인 경우 해당 이번 모험 보스 격파 기록을 보완한다. 과거 모험에서 해금했는지 알 수 없는 장소는 추정 지급하지 않는다.

**구현 연결:** 신규 `Adventure` 정의와 진행 도우미를 `Simulation`의 보스 처치 사건, `UI.renderHp()`, 전투 배경 표시와 연결한다. 기존 이름·몬스터 ID를 맵 테이블로 연결하고 전투 수치를 장소 표시 때문에 중복 계산하지 않는다.

**완료 기준:** 보스 대기 중에는 다음 장소가 열리지 않는다. 보스 처치 후 한 번 열린 장소는 실패·새로고침으로 닫히지 않는다. 지도 미리보기는 장소 이동이나 추가 보상을 실행하지 않으며, 기존 전투는 정상 진행한다. 첫 보스만 반복해서 잡은 누적 기록으로 모든 장소가 열리지 않는다.

### FR06 동료 확장과 조합

**사용자 목적:** 방치 성장, 재화 수집, 스킬 활용, 보스 도전에 맞는 동료를 선택한다.

1. 기존 체육 요정과 응원 요정을 보존하고, 도서관 요정·음악 요정·정리 요정·과학 요정 4종을 추가한다.

2. 동시에 동행할 수 있는 동료는 최대 2명이다. 이전 저장의 기본 조합은 `na`, `yu`다. 이전 두 동료의 `l`, `p`, `c`를 그대로 유지한다.

3. 신규 동료는 `extraCompanions` ID 맵으로 저장한다. 고정 배열에 끼워 넣거나 기존 동료 ID를 바꾸지 않는다.

4. 신규 동료 해금은 아래 보스 이정표와 연결한다. 획득 사실은 정산 후 유지하고, 골드로 올린 강화는 기존 동료처럼 다음 모험에서 Lv.0으로 초기화한다. 기존 두 동료를 포함해 현재 동행한 동료만 효과를 적용한다.

5. 동료 교체 전후 개인 효과와 조합 효과를 표시한다. 성장·수집·보스용 조합을 최대 3개 저장한다. 미보유 동료가 포함된 조합은 이유를 표시하고 적용하지 않는다.

6. 보스 전투 중에는 동료 교체를 잠근다. 일반 적 또는 보스 준비 중에 교체할 수 있다. 교체 직전까지의 경과 시간을 기존 조합으로 정산한 뒤 새 조합을 적용한다.

7. 신규 조합 효과는 명시된 조합에만 적용한다. 기존 `na+yu` 조합에 신규 보너스를 자동 추가하지 않아 이전 저장의 최초 공격력이 바뀌지 않게 한다.

| 신규 동료와 ID | 해금 조건 | 효과와 최대 레벨 | 첫 강화 비용 |
| --- | --- | --- | --- |
| 도서관 요정 `library` | 100 구간 보스 격파 | Lv.1당 경험치 +1%, 최대 Lv.25 | 5,000 골드 |
| 과학 요정 `science` | 200 구간 보스 격파 | Lv.1당 보스 시간 +0.2초, 최대 Lv.25 | 8,000 골드 |
| 음악 요정 `music` | 300 구간 보스 격파 | Lv.1당 재사용 시간 1% 단축, 최대 Lv.20 | 10,000 골드 |
| 정리 요정 `tidy` | 400 구간 보스 격파 | Lv.1당 골드 +1%, 최대 Lv.25 | 12,000 골드 |

신규 동료는 해금 시 Lv.0이며 강화 비용은 네 종류 모두 매 단계 `floor(직전 비용 × 1.8)`로 증가한다. 기존 `GameLimits`의 유한 수치 처리를 적용한다. ID, 해금 조건, 최초 비용, 증가식, 레벨 상한과 효과를 하나의 정의 테이블에서 관리한다. 위 수치는 최초 구현 기준이며 플레이 검증 후 조정할 수 있다. 최대 효과에 도달한 뒤 효과 없는 추가 강화는 구매·추천·자동 구매에서 제외한다.

지정 조합은 두 개만 제공한다. 도서관+정리는 경험치와 골드 보너스에 각각 5%p를 더한다. 음악+과학은 보스 제한 시간에 2초를 더한다. 두 동료 모두 현재 동행 중이며 Lv.1 이상일 때 적용하고, 슬롯 순서는 무관하다. 저장만 한 조합에는 효과가 없다. 다음 모험에서 레벨이 0이면 선택은 유지하되 효과를 중단하고 두 동료를 Lv.1로 강화하라는 안내를 표시한다.

경험치·골드는 기존 `Catalog.bonuses()`가 산출한 보너스와 동료·조합 보너스를 가산한 뒤 기존 획득식에 한 번 적용한다. 예를 들어 최종 경험치 배율은 `1 + 기존 경험치 보너스 + 동료와 조합의 경험치 보너스`다. 기존 아이템·유물 보너스 상한 150%를 유지하고 동료·조합은 각 최대 30%p를 더하므로 합산 보너스 상한은 180%다. 골드의 기존 내림 처리와 경험치의 소수 잔여량 이월을 유지한다. 음악 요정의 단축 상한은 20%이며 조합으로 더 줄이지 않는다. 신규 동료의 보스 시간 증가는 개인 5초와 조합 2초를 합쳐 최대 7초이고 기존 아이템·유물의 시간 효과는 별도로 유지한다.

**시간 보너스 규칙:** 음악 요정 효과는 스킬 사용 순간의 `readyAt`으로 확정한다. 동료를 바꿔도 이미 시작한 재사용 시간이 반복 단축되지 않는다. 기존 `skill.rush`, `skill.night` 사용 시각을 보존하면서 스킬 준비 시각을 보완한다. 과학 요정 효과는 보스 시작 시 제한 시간에 반영한다. 전투 중 음악·과학 동료를 강화해 개인 효과 또는 조합 효과가 늘면 증가분만 제한 시각에 한 번 더한다. Lv.0→1에서 조합이 발동한 경우도 포함한다. `현재 시각 + 전체 시간`으로 재설정하지 않는다. 시계 역행 보정과 정산에도 신규 타이머를 포함한다.

**완료 기준:** v4 저장을 처음 불러온 직후 기존 동료·공격력은 동일하다. 보유하지 않은 동료를 장착할 수 없다. 동료 교체와 강화 전후 표시가 전투 계산과 일치한다. 재사용 시간과 보스 시간이 동료 탈착으로 반복 복구되지 않는다. 정산 후 해금·선택 조합은 유지되고 강화만 초기화된다.

### FR07 캐릭터와 교실 꾸미기

**사용자 목적:** 모험 성취를 캐릭터와 공간에 반영한다.

1. 의상, 소품, 지팡이, 교실 배경, 교실 장식의 5개 영역을 제공한다.

2. 첫 콘텐츠는 영역별 기본형과 해금형을 합쳐 최소 15개 외형을 제공한다. 기존 24종 성장 아이템과 별도 목록으로 관리한다.

3. 기존 업적과 장소 해금으로 외형을 획득한다. 새 재화나 결제 기능은 추가하지 않는다.

4. 미리보기, 적용, 기본 모습으로 되돌리기를 제공한다. 취소하면 기존 외형을 유지한다.

5. 외형은 공격력·경험치·골드 등 전투 수치에 영향을 주지 않는다. 남교사와 여교사 모두에 맞는 표시를 제공한다.

6. 해금과 적용 상태는 저장·백업·다음 모험에서 유지한다. 임시 미리보기는 저장하지 않는다.

7. 꾸미기 SVG나 레이어는 공격 버튼의 입력을 가로채지 않는다. 기존 공격·축하·레벨업 애니메이션과 결합한다. 교실 배경과 장식은 현재 장소가 교실일 때 적용하고 다른 장소에서는 해당 모험 배경을 사용한다. 꾸미기 창에서는 선택한 교실을 별도로 미리 볼 수 있다.

| 영역 | 기본 선택 | 첫 해금 선택 | 두 번째 해금 선택 |
| --- | --- | --- | --- |
| 의상 | 기본 교사 의상 | 조끼 · 100 보스 격파 | 모험 망토 · 400 보스 격파 |
| 소품 | 없음 | 머그잔 · 100 보스 격파 | 수업 수첩 · 200 보스 격파 |
| 지팡이 | 기본 분필 | 별 분필 · 기존 업적 하나 달성 | 무지개 분필 · 300 보스 격파 |
| 교실 배경 | 기본 교실 | 노을 교실 · 200 보스 격파 | 축제 교실 · 400 보스 격파 |
| 교실 장식 | 없음 | 화분 · 기존 업적 하나 달성 | 트로피 · 400 보스 격파 |

업적 조건은 수령 여부와 관계없이 달성 기록으로 확인한다. 장소와 관련된 외형은 해당 보스와 연결된 영구 장소 해금 기록을 사용한다. 외형 ID는 표시 이름과 분리하고 출시 이후 이름을 바꾸어도 같은 ID를 유지한다.

**구현 연결:** `UI.renderCharacter()`, `#teacher-hero`, `#teacher-sprite`, 전투 배경과 신규 `CosmeticCatalog`를 연결한다. 외형 적용 경로를 하나로 모아 캐릭터 변경이 장식을 덮어쓰지 않게 한다.

**완료 기준:** 적용 후 새로고침·백업 왕복·정산에서도 외형이 유지된다. 미보유 항목 적용은 차단된다. 외형 교체 전후 전투 수치는 동일하다. 두 캐릭터와 모바일 화면에서 장식이 잘리지 않고 공격 입력을 방해하지 않는다.

### FR08 업적 진행도와 목표 고정 및 일괄 수령

**사용자 목적:** 가까운 목표를 확인하고 완료 보상을 쉽게 수령한다.

1. 기존 30개 업적에 현재값, 목표값, 진행률, 보상, 수령 상태를 제공한다.

2. 각 업적에 `current(state)`와 `target`을 추가한다. 기존 조건과 같은 기준을 사용한다.

3. 이미 달성한 업적은 골드 소비나 다음 모험으로 현재값이 줄어도 달성 상태를 유지한다. `achReady`와 `extraAchReady`를 성취 판정의 근거로 사용한다.

4. 목표는 최대 3개 고정한다. 직접 고정하지 않았으면 미달성 업적 중 가까운 목표를 추천한다. 비율만으로 어려운 목표를 과도하게 추천하지 않도록 종류와 현재 행동을 함께 고려한다.

5. 받을 수 있는 업적은 기존 알림 표시와 연결한다. 모두 받기는 현재 받을 수 있는 보상만 한 번 지급한다.

6. 일괄 수령은 대상 목록을 최신 상태에서 확정하고 수령 플래그와 보석 합계를 같은 후보 상태에 반영해 한 번 저장한다.

7. 업적 행을 한 번 만들고 숫자·상태만 갱신한다. 진행률 갱신을 위해 전체 행을 100ms마다 새로 만들지 않는다.

**구현 연결:** `Ach.list`, `isReady()`, `isClaimed()`, `claim()`, 신규 `claimAll()`과 `UI.renderAch()`. 기존 업적 ID 및 저장 배열의 인덱스 의미를 유지한다.

**완료 기준:** 7/10에서 처치 후 8/10으로 숫자가 갱신된다. 달성 후 골드를 써도 보상이 취소되지 않는다. 모두 받기를 연속 누르거나 다른 탭으로 이어도 중복 지급하지 않는다. 고정 목표는 백업과 정산에서 유지되며 키보드 포커스가 갱신 중 사라지지 않는다.

### FR09 복귀 성장 보고서와 기록 카드

**사용자 목적:** 자리를 비운 동안의 성장과 다음 행동을 확인한다.

1. 실제 자리비움 시간, 반영된 시간, 이전·현재 레벨, 경험치·골드·보석, 처치 수, 보스 결과를 제공한다.

2. 최대 24시간을 초과한 경우 실제 경과 시간과 보상 반영 시간을 구분한다.

3. 보고서는 자리비움 정산의 이전 상태와 반환 사건, 이후 상태로 생성한다. 자리비움이 1분 이상이거나 레벨 상승·보스 결과가 있을 때 최근 보고서에 추가하며 최대 10개를 보관한다. 자동 표시는 1분 이상일 때 제공한다. 짧은 전환도 정산은 수행하되 0초 재진입이 이전 보고서를 덮어쓰지 않게 한다.

4. `prepareIntroProgress()`, `resume()`, 탭 소유권 획득, 페이지 복귀가 같은 정산 도우미를 사용한다. `enterGame()`은 준비된 보고서를 표시한다.

5. 게임 상태, 반영한 마지막 시각, 보고서 식별자와 본문을 같은 후보 상태로 한 번에 저장한다. 저장 성공 후 보고서를 표시하며 같은 시간 구간을 다시 지급하지 않는다.

6. 보고서 닫기, 다시 열기, 기록 카드 저장은 보상 지급 함수를 호출하지 않는다. 백업 가져오기는 기존 정책대로 가져온 시점부터 시작하며 과거 보고서를 재정산하지 않는다.

7. 보고서에는 현재 가능한 추천 강화 한 가지를 연결한다. 추천을 눌러도 즉시 구매하지 않고 해당 항목으로 이동한다.

8. 기록 카드는 1200×1200 PNG로 저장한다. 캐릭터, 장소, 대표 성과, 날짜, 앱 이름을 담는다. 전체 저장 JSON과 백업 코드를 카드에 포함하지 않는다.

9. 카드의 숫자는 저장된 보고서 값을 사용한다. 그리는 동안 진행한 최신 전투 수치가 섞이지 않게 한다. 이미지 자산과 글꼴 준비를 기다리고 실패 시 다시 저장할 수 있도록 안내한다.

**구현 연결:** 기존 `Simulation.events()`와 `simulate()`, 신규 `Progression.settleAway()`, `ExperienceUI` 보고서, `Sys.download()`와 Canvas 출력. 보상 정산, 보고서 저장, 보고서 표시는 각각 역할을 분리한다.

**완료 기준:** 앱을 완전히 닫았다가 다시 열어도 소개 화면에서 정산된 성과가 보고서에 나타난다. 1시간 자리비움 구간의 보고서를 여러 번 열어도 재화는 늘지 않는다. 30시간 후 복귀하면 최대 24시간만 반영하고 제외된 6시간을 다음 재접속에 다시 지급하지 않는다. 내보내기 실패는 기존 게임 상태를 바꾸지 않는다.

### FR10 다음 모험 미리보기

**사용자 목적:** 정산으로 얻는 것과 다시 시작하는 것을 이해한다.

1. 받을 연수학점, 정산 후 총 연수학점, 연수학점 배율, 다음 모험의 시작 공격력을 표시한다.

2. 유지·초기화 항목을 구분한다. 레벨·아이템 등이 남더라도 기본 강화와 동료 강화가 초기화되어 즉시 공격력이 낮아질 수 있음을 실제 계산값으로 보여 준다.

3. 미리보기와 실제 정산은 공통 `buildPrestigePlan()`을 사용한다. 원본 상태를 변경하지 않고 정산 후 후보 상태를 만든다.

4. 대화상자를 여는 것만으로 보스 시간이 멈추지 않는다. 최종 확인 전에 경과 시간을 정산한다. 받을 학점과 주요 결과가 미리보기와 달라졌다면 갱신한 값을 보여 주고 확인을 다시 받는다.

5. 연속 확인, 탭 소유권 변경, 저장 실패를 처리한다. 한 번의 정산에 하나의 새 `runId`를 부여한다.

6. 자동으로 다음 모험을 시작하지 않는다. 복구 시간이 얼마라는 예측은 별도 검증 전에는 제공하지 않는다.

**유지 항목:** 기존 플레이어 레벨·경험치, 연수학점, 보석, 아이템, 유물, 업적과 수령 대기 상태, 누적 클릭과 보스 처치, 캐릭터와 소리 설정. 신규 안내 상태, 목표 고정, 외형, 동료 해금·선택 조합, 영구 장소 해금, 보고서, 자동화 설정과 사용 예산도 유지한다.

**초기화 항목:** 현재 모험 진행, 골드, 기본 강화, 기존·신규 동료 강화, 현재 적과 보스 도전, 이번 모험의 장소 진행. 스킬의 재사용 시각은 기존 정책에 맞게 보존하고 활성 버프는 종료한다.

**구현 연결:** `Logic.prestige()`, `Data.createDefault()`, `Simulation.getMultiplier()`와 신규 정산 계획 함수. 기존 `#preview-token`을 결과 비교 화면으로 연결한다.

**완료 기준:** 미리보기를 취소하면 정산은 발생하지 않는다. 실제 정산 후의 보존·초기화 항목이 미리보기와 일치한다. 확인 중 보스 실패가 발생해도 오래된 학점으로 정산하지 않는다. 한 번의 정산을 두 번 적용하지 않는다. 자동화 예산 사용액이 0으로 되돌아가지 않는다.

## 6 공통 계산과 실행 구조

### 계산과 화면의 역할

`Simulation`과 공통 계산 함수는 주어진 상태에서 결과를 계산한다. 구매·정산·동료 교체는 후보 상태를 만들고 검증한 뒤 저장한다. 화면은 결과와 가능한 행동을 표시한다. 렌더 함수에서 재화를 지급하거나 스킬을 사용하지 않는다. 시뮬레이션 반복문에서 `catchUp()`과 저장을 포함한 기존 `Logic.upgrade()`나 `Combat.useSkill()`을 다시 호출하지 않는다. 상태 계산 함수와 시간 정산·저장을 조정하는 호출부를 분리한다.

추가 파일은 다음 구성을 제안한다. 실제 파일은 구현 단계에서 생성한다.

| 제안 파일 | 책임 |
| --- | --- |
| progression.js | 구매 견적과 적용, 추천, 업적 진행도, 정산 계획, 복귀 보고서 계산 |
| adventure.js | 장소·동료·외형 정의, 보스 준비 상태 규칙, 해금과 조합 계산 |
| automation.js | 화면이 보이는 동안의 조건 판단, 예산과 자동 행동 |
| experience-ui.js | 첫 모험 안내, 지도, 꾸미기, 보고서, 정산 비교 화면 |

`save.js`와 `game.js`는 기존 저장·전투의 중심으로 유지한다. 로드 순서는 `save → catalog → adventure → game → progression → automation → catalog-ui → experience-ui → app`을 기준으로 한다. 현재 `save.js` 끝에서 `Data.load()`가 즉시 실행되므로 저장 검증은 아직 로드하지 않은 `Catalog`, `Adventure`, `Simulation`을 호출하지 않는다. 검증에 필요한 신규 ID·상한은 기존 `GameLimits`처럼 저장 모듈이 독립적으로 알 수 있는 상수에 둔다. 신규 UI 모듈은 로드 중 앱 UI를 실행하지 않고 기존 앱 초기화에서 연결한다. `index.html`, 서비스 워커의 파일 목록, Node 테스트의 파일 로더를 함께 갱신한다. 같은 전투 공식을 별도 UI 파일에 복사하지 않는다.

### 실행 순서

1. 현재 탭의 플레이 가능 상태와 저장 소유권을 확인한다.

2. 마지막 반영 시각부터 현재까지의 경험치·전투·기존 버프를 정산한다.

3. 보스 등장·실패·처치와 장소 해금을 처리한다.

4. 자동화 조건과 최소 1초 결정 간격을 충족하면 현재 상태에서 한 번 결정한다. 지연된 과거 시점의 자동 결정은 재생하지 않는다.

5. 거래가 있으면 공통 구매·스킬 경로로 후보 상태를 저장한다.

6. 최신 상태를 화면에 반영한다.

보스 준비 중에는 경험치와 재사용 시간만 흐르는 별도 분기를 사용한다. 스킬 지속 시간이나 보스 제한 시간의 경계에서는 기존 실제 시각 순서를 지킨다. 화면 전환은 밀린 수동 공격이나 자동화 명령을 재생하지 않는다.

### 전경과 자리비움의 규칙

| 상황 | 경험치와 기존 자동 전투 | 자동 구매와 신규 스킬 발동 | 사용자 거래 |
| --- | --- | --- | --- |
| 모험 중이며 화면이 보임 | 진행 | 설정과 예산에 따라 진행 | 허용 |
| 탭 숨김 또는 앱 종료 | 복귀 시 기존 규칙으로 정산 | 실행하지 않음 | 불가 |
| 소개 화면 대기 | 진행하지 않음 | 실행하지 않음 | 캐릭터 선택과 시작 등만 허용 |
| 보스 준비 | 경험치만 진행, 공격은 중지 | 자동 스킬 중지, 자동 구매는 별도 허용 설정일 때만 | 강화와 도전 시작 허용 |
| 보고서나 거래 대화상자 | 기존 전투 시간은 진행 | 잠시 중지 | 현재 대화상자에서 허용한 행동만 |
| 다른 탭이 저장 소유 | 소유 탭 기준으로 진행 | 현재 탭에서 실행하지 않음 | 현재 탭에서 차단 |
| 저장 실패 또는 복구 | 기존 보호·임시 플레이 정책 적용 | 중지 | 저장 상태에 맞게 안내 |

보스 준비에서 자동 구매를 허용하는 설정은 기본 꺼짐이다. 준비 창이 열려 있으면 자동화를 중지하고, 창을 닫은 뒤에도 남아 있는 대기 상태에서만 이 설정을 적용한다. 자동 구매의 전경 조건, 예산, 잔액 보존 규칙은 동일하게 적용한다.

## 7 저장 데이터와 호환 설계

### v5 확장 필드

기존 키와 필드는 보존한다. 다음은 추가할 필드의 책임이며 실제 전체 저장 파일 예시는 아니다.

| 필드 | 내용 | 다음 모험 정책 |
| --- | --- | --- |
| onboarding | 안내 버전, 단계, 완료·건너뛰기 | 유지 |

| automation | 실행 설정, 구매 대상, 예산 한도·사용액·보존 골드, 스킬 조건 | 유지 |
| adventure.runId | 현재 모험 식별자 | 새 값 |

미리보기의 DOM 상태, 열려 있는 창, 추천 점수, 파생 공격력은 저장하지 않는다. 계산 가능한 값은 원본 상태와 데이터 테이블에서 구한다. 보고서는 과거 성과를 재현해야 하므로 결과값을 저장한다.

### 마이그레이션 절차

1. 기존 저장 원문을 읽는다. 첫 v5 변환 전에는 원문 복구 사본을 앱 전용 키에 보관한다.

2. 버전별 고정 필수 필드로 기존 v1·v2·v3·v4를 검증한다. 버전이 없던 기존 형식도 현재 지원 정책에 맞게 처리한다.

3. 기존 버전의 의미를 유지하는 v4 상태를 만든다. 정상 필드를 다시 계산해 플레이어의 강화값을 바꾸지 않는다.

4. v5 필드에 기본값을 추가한다. 자동화는 꺼짐, 기존 동료 조합은 `na+yu`, 외형은 현재 캐릭터의 기본형으로 설정한다. 기존 별칭과 시계를 먼저 정규화하고, 스킬 미사용 상태의 `readyAt`은 0으로 둔다. 사용 이력이 있으면 반짝 분필은 기존 사용 시각+60초, 칭찬의 마법은 사용 시각+90초로 복원한다. 일반 불러오기 변환은 진행 중 쿨다운과 활성 버프를 보존하며, 백업 가져오기의 기존 활성 버프 종료 정책은 별도로 유지한다.

5. 확인 가능한 현재 모험의 보스 구간과 기존 성취에 연결된 해금만 복원한다. 새 재화를 지급하지 않는다.

6. v5 필드의 ID, 숫자 범위, 배열 개수, 상태 조합을 검증한다.

7. 저장 소유권과 revision을 다시 확인한 뒤 한 번 저장한다. 실패하면 원본을 덮어쓰지 않는다.

`Data.version`, `createDefault()`, `normalize()`, 가져오기, 내보내기, 초기화, 정산을 함께 수정한다. 신규 필드를 기본값에만 추가하는 방식으로 끝내지 않는다. 이미 변환한 저장에는 마이그레이션 보상이나 해금을 반복 실행하지 않는다.

### 검증과 거래 원칙

- 기존 `relic`, `ach`, `achReady`, `extraRelics`, `extraAch`, `extraAchReady`의 인덱스 의미를 유지한다.

- 알려진 장소·외형·동료·업적 ID만 허용한다. 조합에 중복 동료와 미보유 동료를 허용하지 않는다.

- 예산과 재화는 유한한 비음수로 제한한다. `budgetSpent`가 `budgetLimit`보다 크면 새 자동 구매를 중단하고 설정을 안내한다.

- 새 동료 레벨, 보고서 개수, 문자열 길이, 배열 길이에 상한을 둔다. 전체 내보내기 데이터는 256KiB 이내를 목표로 한다.

- 구버전 클라이언트가 v5 저장을 조용히 초기화하거나 덮어쓰지 않도록 검증한다.

- 백업 가져오기 실패는 기존 진행을 변경하지 않는다. 가져오기가 성공하면 기존 정책처럼 반영 시작 시각을 현재로 설정한다.

- 게임 상태, 거래 비용, 수령 플래그, 예산 사용액은 필요한 범위를 하나의 저장 단위로 묶는다.

- 보고서 열기와 꾸미기 미리보기는 지급·구매를 실행하지 않는다.

- 시계가 뒤로 바뀌는 경우 기존 보정 경로를 사용하고 신규 준비 시각도 보정한다.

## 8 화면 품질과 정적 배포 조건

### 조작성과 접근성

주요 조작은 터치·마우스·키보드로 완료할 수 있어야 한다. 누르는 버튼의 크기는 최소 44px를 목표로 한다. 상태는 색상과 함께 문구로 표시한다. 대화상자는 제목, 닫기, Escape, 포커스 이동과 복귀를 제공한다. 안내나 장식이 전투 입력을 가로채지 않게 한다.

숫자·업적 진행률은 변경된 부분만 갱신한다. 보조기기에 100ms마다 모든 전투 숫자를 읽어 주지 않는다. 중요한 달성·실패·저장 상태만 적절히 알린다. OS의 모션 줄이기 설정과 기존 소리 켜기·끄기를 존중한다.

검토 화면은 320px, 390px, 768px, 1280px 이상과 짧은 가로 화면을 포함한다. `presentation.css`의 후속 적용을 확인하고, 새 CSS를 반복 덧붙여 충돌을 숨기지 않는다.

### 성능

추천과 미리보기는 상태 변경 또는 사용자 요청 때 계산한다. 매 애니메이션 프레임에 전체 아이템과 전체 보고서를 다시 생성하지 않는다. 자동화는 최대 초당 한 번 결정한다. 전체 구매와 보고서 개수에는 상한을 둔다.

기준 개발 환경에서 최대 24시간 자리비움 정산을 측정하고, 기존 같은 저장의 처리 시간과 비교한다. 출시 기준은 기존 대비 2배 이내와 모바일에서의 조작 가능한 복귀를 목표로 하되, 실제 기준 기기와 측정 결과를 검증 기록에 남긴다. 이 값은 현재 측정 결과가 아니라 개선판의 성능 목표다.

### PWA와 자산

`/Hand-Free-Game/` 하위 경로에서 모든 상대 자산이 열려야 한다. 앱 식별자 `/Hand-Free-Game/`, 상대 `start_url`과 `scope`를 유지한다. 핵심 JS, CSS, 캐릭터·몬스터·장소·동료·외형 자산을 준비된 캐시 목록에 포함한다. [S7] [S9]

파일 세트를 버전으로 관리해 구버전 HTML과 신버전 계산 코드가 섞이지 않게 한다. 새 버전 준비 완료를 확인한 뒤 적용한다. 업데이트 과정에서 앱 전용 이전 캐시만 정리한다. 같은 도메인의 다른 웹앱 캐시, 게임 저장, 복구 사본은 지우지 않는다.

필수 자산 캐시가 완료되었을 때 오프라인 준비 완료를 표시한다. 선택 자산을 나중에 받는 경우 준비 상태와 기본 외형 대체를 제공한다. 새 이름의 스크립트를 추가하면 HTML, 캐시, 테스트 로더를 함께 갱신한다.

## 11 개발 AI 토큰 절약 요구사항

### 절약 대상과 적용 원칙

이 절의 토큰은 개발 AI가 처리하는 입력·출력 토큰이다. 게임 상태의 `token`은 연수학점이며 계산과 보존 정책을 변경하지 않는다. 목표는 반복 입력, 중복 탐색, 불필요한 재작성과 재검토를 줄이는 것이다. FR01~FR10, 저장 호환, 입력 안정성, 기능별 완료 기준은 그대로 적용한다.

개발 문서는 필요한 내용을 찾는 짧은 안내와 상세 규격으로 나눈다. OpenAI의 공식 설명도 작업과 관계있는 지침을 선택해 읽고, 항상 적용되는 지침을 짧게 유지하는 구성을 권한다. [O1]

파일로 보관한 내용도 모델이 읽으면 문맥에 포함된다. 따라서 파일 경로만 남기는 것과 실제로 필요한 절만 읽는 것을 함께 적용한다. 파일에 접근할 수 없는 환경에서는 필요한 절을 직접 제공한다. API의 프롬프트 캐시는 별도 기능이며, 캐시된 입력도 API의 분당 토큰 제한에 포함된다. 캐시 사용을 구독 사용량 감소율이나 토큰 0으로 환산하지 않는다. [O3]

### TE01 문서를 한 곳에서 관리하고 필요한 절만 읽기

- 완성 PRD의 저장소 내 권장 경로는 `docs/PRD.md`다. 이름은 프로젝트 관례에 맞춰 정할 수 있으며, 이 경로가 이미 존재한다고 가정하지 않는다.
- 이 문서의 0절은 읽기 안내다. 해당 FR과 영향을 받는 공통 규칙·완료 기준을 찾아 읽고 상세 요구사항을 적용한다.
- 기존 `AGENTS.md`가 있으면 적용되는 지침을 먼저 확인한다. 전체 PRD, 긴 테스트 로그, 과거 대화를 지침 파일에 복사하지 않는다. 필요한 공통 규칙과 문서 위치만 연결한다.
- 같은 기능 정의·수치·저장 정책을 여러 요약 문서에 중복 관리하지 않는다. 작업표는 PRD 버전, 작업 ID, 참조 절과 완료 조건을 가리킨다.
- 관련 없는 디자인·자료 조사·전체 코드 설명을 모든 작업의 시작 조건으로 추가하지 않는다. 실제 의존성이 확인되면 읽기 범위를 넓힌다.

`docs/PRD.md`, 아래 작업표, `docs/HANDOFF.md`는 이 프로젝트의 선택적인 관리 방식이다. `AGENTS.md`와 달리 이 이름의 파일을 Codex가 반드시 요구하거나 자동으로 읽는다고 전제하지 않는다. [O2]

**완료 확인:** 다음 작업을 시작할 때 PRD 전체 재전송 없이 해당 FR, 공통 규칙과 최신 작업 상태를 찾을 수 있다. 축약 지시만 보고 확인하지 않은 요구사항을 완료 처리하지 않는다.

### TE02 재사용할 코드와 변경 범위부터 확인하기

작업 시작 시 적용되는 저장소 지침, 현재 커밋, 수정·스테이징·미추적 파일을 확인한다. 인계 기록과 차이가 있으면 바뀐 파일부터 살펴본다. 이미 확인한 내용을 목적 없이 전량 재독하지 않는다. 변경 확인, 문맥 복구, 의존성 이해, 오류 분석이나 검증에 필요하면 해당 범위를 다시 확인한다.

`rg`로 함수와 호출 위치를 찾고 필요한 범위를 읽는다. 출력이 잘리면 검색어·파일·범위를 좁혀 다시 확인한다. 문맥에서 빠진 부분을 추정으로 메우지 않는다. 전체 파일 확인이 필요한 초기화·상태 전환·저장 경로는 충분한 범위를 읽는다.

다음은 저장소에서 사용할 수 있는 탐색 예다. 첫 세 명령의 결과를 함께 보아 스테이징된 변경이나 새 파일을 놓치지 않는다.

```bash
git status --short
git diff --name-only
git diff --cached --name-only
rg -n 'getUpgrade|buyItem|prepareIntroProgress|prestige' game.js app.js
```

기존 엔진·구매 DOM·SVG와 데이터 테이블을 재사용한다. 이번 작업과 관계없는 파일 재정렬, 전체 포매팅, 프레임워크 교체는 하지 않는다. 새 장소·동료·외형의 차이는 가능한 범위에서 정의 데이터와 기존 표시 코드로 표현한다.

**완료 확인:** 변경 파일과 이유가 작업 목표에 연결된다. 같은 동작을 별도 계산식으로 복제하지 않는다. 공통 함수나 저장 규칙 변경 시 직접 호출부까지 검토한다.

### TE03 기능별로 읽을 파일과 검사 범위 지정하기

### TE04 테스트의 출력량을 줄이고 필요한 검증을 유지하기

수정 직후에는 영향받는 검사를 먼저 실행한다. 전투·저장·카탈로그 공통 계산이나 모듈 로드 순서를 바꾸면 연결된 회귀 검사로 범위를 넓힌다. 각 단계에서는 10절의 해당 단계 완료 기준과 영향받는 회귀 검사를 적용한다. 최종 공개 전에는 9절의 전체 수용 기준과 10절의 최종 검증을 적용한다.

검사 결과를 재사용하려면 관련 코드·미추적 파일·테스트·픽스처·로드 순서·명령·실행 환경이 같아야 한다. HEAD가 같다는 이유만으로 재사용하지 않는다. 문서만 바뀌고 코드가 그대로인 경우처럼 영향이 없으면 이전 결과의 검증 대상과 실행 시점을 함께 참조한다. 수정된 기능에 이전 버전의 통과 결과를 붙이지 않는다.

검사 원문과 브라우저 결과 JSON은 기록 파일에 보관한다. AI에는 명령, 실행 건수, 통과·실패 요약, 실패한 검사와 필요한 오류 구간을 제공한다. 로그를 줄여도 실행 종료 코드와 실패 여부는 확인한다. 같은 조건의 성공 로그를 반복 출력하거나 읽지 않는다. 새 모듈을 추가했다면 실제 앱과 Node 테스트의 로드 순서를 맞춘다. 통과를 위해 필요한 모듈을 가짜 객체로 대체하거나 기존 검사를 제외하지 않는다.

현재 `tests/browser_smoke.py`는 반복 가능한 `--check` 문자열 필터를 제공한다. 예를 들어 기존 welcome 검사를 고를 때 다음처럼 실행할 수 있다. URL은 실제 켜 둔 개발 서버 주소에 맞춘다. [S10]

```bash
python tests/browser_smoke.py http://127.0.0.1:8000/ --check welcome --output /tmp/hand-free-welcome-check.json
```

현재 스크립트는 선택된 검사가 0개일 때도 종료 코드 0을 반환할 수 있다. 결과 JSON에서 `total > 0`, 실제 검사 이름, 필요한 검사가 모두 실행됐는지를 확인한다. `--check`가 제공된 상태에서 0개가 선택되면 실패로 처리하도록 검사 도구 보완을 개발 검증 작업에 포함한다. 화면 캡처 옵션을 실행하지 않은 결과를 시각 검수 완료로 표시하지 않는다. 첫 오프라인·버전 업데이트 검증은 기존 전체 브라우저 검사 통과와 별도로 수행한다. [S10]

**완료 확인:** 재사용한 결과에는 대상 코드와 실행 조건이 있고, 새 결과에는 실제 실행된 검사가 있다. 필터 0건, 건너뛴 화면 캡처, 미실행 신규 검사를 통과로 표시하지 않는다.

### TE05 다음 작업을 위한 짧은 기록 유지하기

개발 중 `docs/HANDOFF.md` 또는 기존 동일 목적 파일에 최신 상태를 유지한다. 공식 예제도 다음 작업의 판단에 필요한 맥락을 기록하는 방식을 소개한다. 아래 양식과 파일명은 이 프로젝트에 맞춘 제안이다. [O2]

```text
PRD 버전:
브랜치와 기준 커밋:
미커밋 변경 및 관련 파일 해시 기록 위치:
현재 단계와 작업 ID:
FR01~FR10 상태: 대기 / 진행 / 구현 완료 / 검증 완료
이번 변경과 충족한 완료 기준:
변경 파일과 중요한 연결점:
검증 명령·결과·환경·상세 기록 위치:
남은 문제와 다음 작업:
```

긴 대화와 모든 성공 로그를 누적 복사하지 않고 최신 상태를 갱신한다. 토큰 절약만을 위한 별도 메모리 서버나 복잡한 문서 생성 도구는 추가하지 않는다. 상세 증거가 필요하면 별도 로그를 연결한다. 새로운 대화에서는 이 기록과 실제 작업 트리를 비교한 뒤 이어서 진행한다. 결정 확인, 문맥 복구, 의존성 이해나 검증에 필요하면 해당 코드와 근거를 더 확인한다.

일반 완료 보고는 완료 항목, 주요 변경, 검증, 남은 문제, 다음 작업의 다섯 항목으로 쓴다. 전체 PRD·완성 코드·전체 로그를 답변에 다시 출력하지 않는다. 실패나 중요한 제한사항은 해결에 필요한 만큼 설명한다.

**완료 확인:** 다른 작업자가 긴 대화 전체를 읽지 않고도 현재 상태와 다음 행동을 확인할 수 있다. 구현 완료와 검증 완료가 구분된다.

### TE06 운영 중 AI 호출 없이 기능 제공하기

강화 추천은 기존 계산식과 선택 전략, 보스 안내는 전투 사건과 조건표, 복귀 보고서는 정산 결과와 문구 템플릿으로 만든다. 지도 이야기와 꾸미기 설명도 정적 데이터로 제공한다. 이 개선 범위에서 추가하는 게임 기능의 운영 중 LLM 호출 목표는 0회다.

추천·보고서·업적 판정에 외부 AI SDK, API 키, 호출 서버를 추가하지 않는다. 개발 작업의 인계 기록과 로그는 게임 저장 데이터에 넣지 않는다. 서비스 워커의 자산 캐시와 개발 AI의 문맥·토큰 사용량은 별개로 관리한다.

**완료 확인:** 네트워크가 없는 상태에서도 준비된 자산과 저장 정보로 해당 기능이 동작한다. 추천·보고서·보스 안내를 반복 실행해도 AI API 요청이 발생하지 않는다.

### TE07 절감 효과를 확인하는 기준

목표 수치는 모델별 실제 측정 없이 임의의 절감률로 정하지 않는다. 개발 도구가 사용량을 제공하면 같은 종류의 작업, 같은 모델·환경, 같은 품질 기준에서 입력·출력·캐시 항목을 그 도구의 정의대로 기록한다. 캐시 항목이나 추론 항목을 총량에 중복 합산하지 않는다.

토큰 수가 제공되지 않으면 PRD 전체 재전송 횟수, 이유 없는 동일 코드 재읽기, 반복된 로그 출력, 재작업 횟수를 관찰 지표로 사용한다. 문자 수·파일 크기·호출 횟수를 실제 토큰이나 과금액이라고 표시하지 않는다. 검증 실패와 기능 누락이 늘어나면 절약 규칙의 적용 범위를 조정한다.

**완료 확인:** 완료 기준과 검증 범위를 유지하면서 반복 입력·탐색·재작업을 줄였는지 설명할 수 있다. 실제 절감률은 비교 기록이 있을 때만 보고한다.

### 바로 사용할 개발 지시문

다음 문구는 완성 PRD를 `docs/PRD.md`로 두었거나 첨부해서 개발 AI가 내용을 읽을 수 있는 경우에 사용한다. 다른 경로를 사용했다면 실제 위치로 바꾼다. 작업 인계 파일이 없으면 현재 코드와 검증 기록으로 진행 상태를 확인하고 첫 미완료 작업부터 시작한다. 기반 구현이 없으면 0단계부터 시작한다. 여러 단계를 승인받은 작업은 그 범위 안에서 다음 묶음으로 이어서 진행한다.

```text

적용되는 저장소 지침과 현재 변경 상태를 먼저 확인해.

PRD 0절, 해당 FR, 영향을 받는 공통 규칙과 완료 기준을 읽고 필요한 코드·호출부를 확인해.
기존 계산과 UI를 재사용해 작업 묶음마다 구현·검증·인계를 완료하고, 이번에 요청받은 구현 범위가 끝날 때까지 이어서 진행해.
저장·전투·입력·PWA 검증을 유지하고, 동일 입력의 검증 결과는 근거를 기록해 재사용해.
새 기능에 운영 중 AI 호출을 추가하지 말고, PRD 전체·전체 코드·성공 로그를 반복 출력하지 마.
HANDOFF.md를 갱신하고 완료·변경·검증·남은 문제·다음 작업을 간단히 보고해.
```

특정 기능을 지정할 때는 첫 문장을 ‘FR02의 강화 비교와 묶음 구매를 구현해’처럼 바꾼다. 선행 공통 계산·저장 기반이 없으면 필요한 기반 작업을 함께 처리하고 기록한다. 기능을 구현하라는 지시 없이 문서 수정만 요청받은 경우에는 PRD를 수정한다.
